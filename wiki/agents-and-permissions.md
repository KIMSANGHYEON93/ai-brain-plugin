# 에이전트·커맨드·스킬과 권한 등급

← [[index]] · 관련: [[release-and-gates]]

## 권한 모델 — '제안'이 천장이다

에이전트 등급은 **읽기 ⊂ 추가 ⊂ 제안**이고, 그 위는 어떤 에이전트에게도 열리지 않는다(`README.md` §권한 등급).

| 에이전트 | 등급 | 하는 일 | 하지 않는 일 | 정의 |
|---|---|---|---|---|
| `brain-reviewer` | 읽기 | 상태 점검, 승격 후보·지식 갭 보고 | 지식을 바꾸는 모든 쓰기 | `agents/brain-reviewer.md` |
| `brain-syncer` | 추가 | Notion 새 행 생성, 실행 기록 | 이동·삭제·본문 편집 | `agents/brain-syncer.md` |
| `brain-librarian` | 제안 | Inbox 분류, `status: draft` 카드 초안, 관계 추가 | `verified` 승격, 런북 작성, 덮어쓰기 | `agents/brain-librarian.md` |
| `brain-verifier` | 제안 | 중복·손상 탐지, 격리 페이지로 **이동** | 영구 삭제 | `agents/brain-verifier.md` |

**어떤 등급으로도 열리지 않는 것:** `verified` 승격 · 런북 신규 작성 · 기존 md 덮어쓰기·삭제 · Notion 페이지 영구 삭제 · 클라우드 휴지통 이동. 전부 사람 몫이다.

**하나의 예외:** 실행 기록 `brain_run_log`는 '읽기' 등급에도 열린다. 지식을 바꾸지 않고 자기가 무엇을 했는지만 남기기 때문이고, 읽기 전용 에이전트가 자기 실행을 기록하지 못하면 "실제로 돌았는가"를 사람이 확인할 방법이 사라진다(README).

### 등급은 두 겹으로 지켜진다 — 그리고 두 겹이 다르다

1. **도구 허용 목록** — 각 에이전트 프론트매터의 `tools:`. 여기 없는 도구는 호출 자체가 안 된다.
2. **본문 지시문** — "덮어쓰지 않는다", "삭제하지 않는다" 같은 문장.

둘이 일치하지 않는 곳이 있다. 바꿀 때 가장 주의할 부분이다.

- **`brain-librarian`은 `Write`를 갖고 있다.** 새 draft 카드를 만들려면 필요하지만, `Write`는 기존 파일도 덮어쓸 수 있다. "기존 파일 덮어쓰기는 하지 않는다"는 도구가 아니라 **지시문으로만** 막혀 있다.
- **`brain-reviewer`의 본문은 "아무것도 쓰지 않는다 … 캡처·로그·관계 추가조차 하지 않는다"인데 `tools:`에 `brain_run_log`가 있다.** 위의 예외 규칙 때문에 의도된 것이지만, 에이전트 본문만 읽으면 모순으로 보인다. 본문을 고친다면 볼트 쪽 런북을 고쳐 다시 컴파일해야 한다([[index]] §바꾸기 전에).
- **`brain-syncer`·`brain-verifier`는 `Bash`를 갖는다.** 볼트의 `_mcp/notion_sync.py`로 diff를 계산하라는 지시 때문이다("목록을 눈으로 옮겨 적지 않는다"). `Bash`는 사실상 무엇이든 할 수 있으므로, 이 두 에이전트의 '추가'·'제안' 경계는 지시문 의존도가 높다.

> 새 에이전트를 추가하거나 `tools:`를 넓힐 때는 **도구 목록이 등급을 넘지 않는지**부터 본다. 지시문은 모델이 따르기로 할 때만 작동한다.

## 에이전트가 공통으로 지키는 실행 규칙

`brain-syncer`·`brain-verifier` 본문에 같은 블록이 들어 있다(두 파일에 복사돼 있다).

- **`run_id` 필수.** 한 논리 작업에 키 하나(예: `sync.2026-09-04T1430`). `:`는 쓰지 않는다 — 윈도우 파일명과 YAML 양쪽에서 깨진다.
- **키는 `(run_id, step)` 복합키.** 2단계부터 `step=`을 붙이지 않으면 같은 키로 취급돼 두 번째 기록이 **조용히 사라진다.**
- **`status: noop`은 실패가 아니다.** 이미 기록됐다는 뜻이다. noop을 실패로 읽고 키를 바꿔 재호출하면 멱등성이 무너진다.
- 실행 기록은 `brain_log`(사람 경험)가 아니라 `brain_run_log`(`35_Runs/`)에 남긴다.

**정지 조건**도 에이전트마다 수치로 박혀 있다 — 예: verifier는 격리 대상이 **5건을 넘으면** 실행하지 않고 목록만 보고한다("그 규모면 개별 오류가 아니라 절차 결함일 가능성이 크다"). syncer는 COUNT 불일치 2회 연속, 같은 에러 3회 연속이면 중단한다.

## 커맨드 — 에이전트를 엮는 순서

| 커맨드 | 하는 일 | 쓰는 에이전트 |
|---|---|---|
| `/brain-weekly` | 주간 정리 5단계: 상태 점검 → Inbox 분류 → 미러 검증(미반영이면 동기화 후 재검증) → 사람이 결정할 것만 보고 → 기록 | reviewer → librarian → verifier(+syncer) |
| `/brain-sync` | Notion 미러 동기화 후 `COUNT = DISTINCT = 볼트 용어 수` 확인. 어긋나면 verifier로 | syncer → verifier |
| `/brain-promote` | 승격 사다리(로그→런북→스킬→에이전트) 후보 보고. **규칙 문구를 그대로 옮긴다** — "runs 2 < 3"처럼 | (에이전트 없이 `brain_promotion_candidates` 직접) |

`/brain-sync`는 `$ARGUMENTS`로 범위를 한정할 수 있다(예: 런북만).

## 스킬 — `notion-mirror-sync` v1.3

`skills/notion-mirror-sync/SKILL.md`. 볼트가 원본이고 Notion은 **메타데이터 + Drive 링크만** 담는 검색용 미러다. 본문은 복사하지 않는다.

- **절차 전문은 이 파일에 없다.** 실행 전 `brain://runbook/RB_Notion_미러_동기화`를 읽는다. 스킬 버전(1.3)은 원본 런북 버전과 같게 유지한다.
- 리소스를 못 읽을 때만 쓰는 **5줄 요약 절차**가 있다 — 양쪽 목록을 매번 새로 조회 → 프로그램으로 diff → 생성 직전 `WHERE Name IN (...)` 재확인 → Drive 파일 ID 배치 조회 → ≤20건씩 생성 후 COUNT/DISTINCT 검증.
- **실패 유형 표**(Source Logs 숫자 오류, multi_select 옵션 누락, Drive 검색 0건, 같은 Name 2행, 한글 낱자 손상)가 스킬·syncer·verifier 세 곳에 나뉘어 있다. 상세는 런북 §6이다.

### 한글 낱자 손상(H2)이 왜 특별한가

`agents/brain-verifier.md`가 가장 길게 설명하는 실패다. 낱자가 깨지면(`컨텍스트`→`컴텍스트`) 문자 자체가 달라서 정규화 비교가 "볼트에 없는 이름"으로 오인하고, **다음 라운드에 정상 철자로 새 행이 또 생긴다.** 그래서 정규화 diff로는 못 잡고, 정렬된 전체 목록을 사람이 훑어 인접한 비슷한 이름을 찾은 뒤 `Drive Link`를 대조해 확정한다. One-liner만 깨진 경우는 **고치지 않는다** — 원본은 볼트 md다.

## 바꿀 때 확인할 것

- `skills/`·`agents/`를 바꾸는 커밋에는 **`Compiled-From: <런북> v<버전>` 푸터**를 단다([[release-and-gates]]). 없으면 git만 보고 파생 관계를 확인할 수 없다.
- 워크스페이스 id를 본문에 적지 않는다. 격리 페이지 id도 런북 §6-G에서 읽는다 — 게이트 ⑤가 막는다.
- 이 저장소에는 테스트가 없다. 바꾼 뒤 확인 수단은 pre-push 게이트(매니페스트 JSON 유효성 등)와, 실제 설치 후 `/brain-promote` 실행뿐이다.
